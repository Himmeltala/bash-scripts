# idex 工程目录约定

## 目标

打开目录就能看出系统有哪些能力，以及每块代码属于哪个能力；改一个功能时只在一个目录树里活动。整体采用 **feature-first（按功能分包）**，功能内部再按技术类型分层。

## 总体结构

```
idex/
  bin/idex                 入口
  lib/                     bash 加载器与命令行
  src/idex/                Python 包
    engines/               Node、JVM 引擎
    web/                   转发进程、路由、版本库查询
  web/
    src/                   前端源码
    dist/                  构建产物，不入库
  tests/                   Python 回归
  docs/                    工程约定与设计说明
```

后端是 Python 常见的 `src` 布局；bash 只是启动胶水，留在 `lib/`；测试与文档用复数目录名。

## 前端核心思想

### 按功能分包，而不是按层分包

目录第一层按业务能力切：`browse`、`changes`、`engines`、`log`、`sync`、`workspaces`、`editor`。一个功能的页面、组合式函数与纯函数都放在同一个目录下（colocation），不散落到全局的 `components/`、`composables/` 里。

### 功能内部按类型分层

```
features/<功能>/
  components/    只放 .vue
  composables/   只放 use*.js
  lib/           无框架依赖的纯函数、接口表、格式化
```

编辑器的 `core/` 放语言扩展、处理器、位置计算、主题与预览模型，与 UI 组件分开。

判断标准：

- 有模板、生命周期或响应式渲染 → `components/`。
- 以 `use` 开头、封装响应式状态或副作用 → `composables/`。
- 纯输入输出、不发请求、不依赖 Vue → `lib/`。
- 只被一个功能使用 → 留在该功能的目录里。

### 全局目录只放真正跨功能的东西

`utils/`、`stores/`、`plugins/` 是应用级公共层。某段代码只有两个以内功能在用，优先放功能目录，确认稳定后再上移，避免公共层变成杂物间。

## 新文件放哪里

1. 先问它属于哪个业务能力，放进对应 `features/<功能>/`。
2. 再问它是什么类型：组件、组合式函数还是纯函数。
3. 都不属于任何功能，才算应用级公共代码。
4. 多个前端工程共用，放到仓库的 `lib/web-shared`，不要放进 idex。

## 反面做法

- 顶层按 `components/`、`composables/`、`utils/` 全量平铺，功能代码散在三四个目录里。
- 功能目录里 `.vue`、`use*.js`、纯 `.js` 混放，只能靠文件名猜类型。
- 把只有一个功能用的小工具提前放进全局 `utils/`。
- 用 `pages/`、`views/` 套一层路由：这里是单页工作台，没有路由层级。

## 与 Feature-Sliced Design 的关系

采用 FSD 的核心思想：按功能切、功能内聚、共享层独立。没有照搬它的 `app / pages / widgets / features / entities / shared` 全部层级，规模不需要，层级多了反而增加跳转成本。
