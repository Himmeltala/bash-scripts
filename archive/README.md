# archive

归档类工具。

## zipx

把 `zip` 与 `unzip` 常用的那几种组合收进一个界面：压缩、解压、查看与校验、包内增删。不带参数打开菜单，先选动作再勾目标；带参数直接执行，进脚本也方便。只管 zip 包，不管 tar.gz 与 7z。

### 用法

```
zipx                     打开菜单
zipx pack 目录 文件       打包，默认排除 .git、target、node_modules 等
zipx pack -o 名字.zip 目录
zipx pack -e 目录         加密，密码由 zip 自己交互提示输入两次
zipx unpack 包.zip        解到当前目录
zipx unpack 包.zip -d 目标目录
zipx extract 包.zip 条目  只提取包内指定条目
zipx list 包.zip          列出包内文件
zipx test 包.zip          校验包的完整性
zipx add 包.zip 文件      追加进已有包，撞同名条目是更新
zipx rm 包.zip 条目 -y    删包内条目
zipx -n ...               只打印要执行的命令，不落盘
zipx --help               显示帮助
```

界面用方向键移动、空格勾选、回车确认。`--menu` 与 `--checklist` 的结果 whiptail 写在 stderr 上，与 dialog 相反，脚本里用 `3>&1 1>&2 2>&3` 把两边调换过来取。

非交互环境（管道、脚本、CI）下探不到终端，自动退回编号输入：菜单列成编号让人选一个，复选让人一次输多个编号。输入用完了就按取消处理，退出码 3。

### 缺省与省略

- 不带参数开菜单；只给了条目没给动作时按 `pack` 处理。第一个参数是 `.zip` 时脚本会提示一句「要解压的是包，用 unpack」，这是最容易搞错的一步。
- 包名默认取当前目录名加 `.zip`，用 `-o` 换。
- 解压目标目录默认当前目录，用 `-d` 换，目录不存在会建。
- `pack` 的动作是压缩不是解压，`unpack` 才是解压。

### 安全约定

三件事刻意做成要人点头才做：

- **已有的包不静默覆盖。** `pack` 撞上同名包直接拒绝，要覆盖得加 `--overwrite`。包里可能是上一次打包的东西，盖掉就找不回来。
- **解压默认不覆盖同名文件**（`unzip -n`），要覆盖得加 `--overwrite`（`unzip -o`）。解压出错最常见的后果就是把别人的文件盖掉。
- **删包内条目前确认。** 交互时弹一次确认框；非交互环境不给 `--yes` 就直接拒绝，因为 `zip -d` 是直接从包里摘掉，没有回收站。

加密只用 `zip -e`，密码由 zip 自己提示输入，不走命令行。不用 `-P`：那个密码会留在进程列表里，同一台机器上 `ps` 就能看见。

解压前先看一遍包内条目名，绝对路径、Windows 盘符、含 `..` 的条目一律拒绝执行。这类包解出来会写到目标目录之外（zip slip）。unzip 6.0 自己会拦一部分，但各版本行为不一致，不指望它。

### 默认排除

`pack` 默认跳过 `.git`、`.svn`、`.idea`、`node_modules`、`target`，这几类要么是版本库元数据，要么是构建产物与依赖，塞进包里只让包变大。规则加在被选中条目那一层之下，选中 `proj` 时排掉的是 `proj/.git` 与它下面的所有东西；显式选中的条目本身不排除，选 `.git` 就是要它。`--no-exclude` 关掉默认规则，`--exclude 模式` 再加一条自己的（按 zip 的规则匹配归档内路径，可重复）。

### 中文文件名

实测结论，两种情况分开看：

- **解压本机打的包没有问题。** zip 3.0 编译时带了 `UNICODE_SUPPORT`，locale 为 UTF-8（本机 `zh_CN.UTF-8`）时自动给非 ASCII 名置 UTF-8 标记。实测打出来的包 `flag_bits` 为 `0x800`，Windows 解压中文名正常，不需要额外加 `-UN=UTF8`。
- **解压老工具在 Windows 上打的包会是乱码。** 这类包把 GBK 字节直接写进条目名且不置 UTF-8 标记，unzip 按 cp437 解出成 `╛╔░ⁿ╬─╝■` 这样的框线字符。unzip 6.00 **不支持**指定包内编码（加 `-O` 报用法错，退出码 10），所以这件事在本机没有干净解法。脚本探测到这种条目名会提示一句，要正常显示得换 7z、bsdtar 这类工具。

探测靠字符本身：正常文件名不会成片出现框线与块字符（`U+2500` 到 `U+259F`、`U+25A0` 到 `U+25FF`），用 `grep -P` 查一遍。字节层面验不出来，因为 unzip 已经把名字转成本地编码了。

### 退出码

| 码 | 含义 |
| --- | --- |
| 0 | 成功 |
| 1 | 操作失败：包读不了、包坏了、zip 没有可打包的东西、找不到条目等 |
| 2 | 用法错误，与 `mvnstart`、`killport` 一致 |
| 3 | 用户取消：菜单里按取消、菜单模式输入用尽、删条目没确认 |

`unzip` 自己的失败码有 9、10、50 这些，脚本统一收成 1，调用方按上表判断即可，不必去查 unzip 的码表。

### 实测记录

- 空目录会存成目录项，解压时也建出来。
- 符号链接默认跟随，存的是链接指向的内容，解出来是一份普通文件副本。要存链接本身得给 zip 加 `-y`，本工具没开放这个开关。
- 坏掉的符号链接：zip 报 `zip warning: name not matched` 并跳过该条目，其余照常打包，退出码不变。
- 条目名与包名带空格都正常，命令打印时按 `%q` 转义，复制粘贴回去能直接跑。

### 实现上的坑

- **界面能不能用必须在命令替换之外判一次。** 界面函数是按 `out=$(ui_menu ...)` 调的，命令替换会把 stdout 换成管道，在替换里判 `[[ -t 1 ]]` 永远是假，界面会永远退化成编号输入，而且不报错、看不出异常。所以启动时判一次写进 `UI_MODE`，之后一律读这个变量。这个 bug 是靠伪终端里跑一遍才现形的，直接跑根本看不出来。
- **whiptail 的结果在 stderr 上**，不是 stdout，与 dialog 相反，`man whiptail` 的 `--checklist` 一节写明了。
- **清单按行读，名字里的换行必须拒掉。** 勾选界面与 `unzip -Z1` 都是一行一个名字，换行会被拆成两条互不相干的记录。撞上直接在动手前报错退出。
- **`--dry-run` 的检查要放在动作之后。** 预演模式下 zip 没真跑，包文件当然不存在，一开始把「包有没有生成」放在 `run_cmd` 后面判，预演必定误报失败。
- **列表框高度要给够。** whiptail 的 `--menu`、`--checklist` 高度参数给 0 不是自动撑开，列表框只显示一部分且滚动不正常；按条目数与终端大小算一个高度再传。
- **包名以减号开头会被 zip 当成选项**，统一在前面补 `./` 再传。
- **`unzip -Z1` 的输出已经过编码转换**，看出乱码要靠字符特征，不能靠字节校验。
- **`grep -P` 是探测乱码名的依赖**，没有 PCRE 支持时探测函数返回「不是乱码」，只影响提示，不影响解压。
- **替换测试不能只改几个字节。** 往包中间写几个字节不一定落在被校验的数据区，`unzip -t` 照样报正常；要造损坏的包就截断，把中央目录切掉。

### 已知限制

- 只管 zip，不支持 tar.gz、7z、分卷包。
- 不支持指定包内编码（本机 unzip 版本所限，见上）。
- 符号链接一律跟随，没有「存链接本身」的开关。
- 菜单模式在管道里输入耗尽时按取消退出，退出码 3；要脚本化就用带参数的形式。
